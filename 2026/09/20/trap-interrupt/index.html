Trap与Interrupt的理解

写于：2026-09-20

写在前面

最近一直在准备秋招的事项，也马上就得回学校干那个SHABI课题了，很久没有更新博客了。。。最近花了点时间梳理了一下Trap和Interrupt的概念，这个是在实习的时候从英飞凌芯片中接触了解到的。

首先在英飞凌的Tricore架构中，Trap 是 TriCore CPU 架构提供的一种异常事件处理机制。当 CPU 或系统检测到特定异常条件，或者软件主动触发特定 Trap 时，CPU 会中断当前正常执行流，保存必要的执行上下文，并通过 Trap Vector Table 转移到对应的 Trap Handler 进行处理，这一点触发的底层逻辑和我们经常会用到的中断，也就是interrupt很像，但是核心的含义却不一样，简单来说中断更像是请求响应机制、Trap则是异常控制流机制。后面会详细说明。Trap 不等于“程序报错”，更准确地说是一套特殊事件/异常的控制流转移机制。芯片手册中对于Trap的定义如下：

查 TC3xx 的 OS 异常处理代码时，启动文件分别初始化 BIV 和 BTV这两个寄存器。外设中断从 BIV 进入，访问保护错误却从 BTV 进入。同样是“当前程序被打断”，为什么要准备两张表？如果调试器已经停在 OS 的 Handler，原来出问题的指令又在哪里？

关键是 TriCore 把 Interrupt 服务请求和 Trap 事件交给两套不同的分发机制。Cortex-M4 则把外部 IRQ、HardFault 等纳入同一套 Exception 机制。名字相似，分类方法并不一样。

1. Trap 和 Interrupt 究竟按什么区分

CAN 控制器收到一帧数据，向 CPU 发出服务请求：中断系统仲裁优先级，再按 BIV 找到 ISR。程序执行 LD.W 时读取了无权访问的地址：CPU 识别出保护错误，按 Trap Class 从 BTV 进入 Trap Handler。前者回答“哪个服务请求该由 CPU 处理”，后者回答“发生了哪类异常事件”。

TriCore Interrupt TriCore Trap
入口由什么索引 待处理请求的优先级号 PIPN Trap Class Number，即 TCN；同类中的原因看 TIN
入口在哪里 BIV 指向的中断向量表 BTV 指向的 Trap 向量表
会不会被普通中断屏蔽条件挡住 ICR.IE = 0 或 PIPN ≤ ICR.CCPN 时暂不响应 不受 ICR.IE/CCPN 这套条件屏蔽
典型例子 定时器到期、CAN 收到报文 访问保护错误、非法指令、SYSCALL、NMI

但是也不能直接用“外部事件是 Interrupt、CPU 内部错误是 Trap”来定义。比如说TriCore 的 NMI 虽然叫 Non-Maskable Interrupt，实际走异步 Trap 路径；SYSCALL 是软件主动触发的 Trap，正常使用时根本不是故障。Trap 既可能同步于某条指令，也可能异步发生。真正决定入口的是事件走中断优先级系统，还是 Trap Class 系统。

整体来说，不管是Trap还是interrupt，背后的本质都是触发后去根据相应的寄存器里存放的向量表的基址跳转，然后根据向量表定义好的地址再根据硬件机制判断当前触发的是哪种类型的中断/异常？再根据向量表的定义跳转到指定地址，执行一些上下文保存操作之类的操作(汇编语言)。对于Tricore的架构而言，Trap和Interrupt是有两个单独的向量表分别维护的，示意图如下：

BIV 和 BTV 表内的入口是可执行代码，短短几条指令通常再跳往完整 Handler。这也解释了为何调试器停在 OS Handler 时，当前 PC 已经不在向量槽内。

2. 例子1：CAN 中断为何有时进不了 ISR

假设 CAN 控制器已经提出服务请求，中断路由把待处理请求的优先级号送到目标 Core，记作 PIPN。CPU 并非一收到请求就立刻跳走，还要满足两个条件：全局中断使能位 ICR.IE = 1，并且 PIPN 高于当前 CPU 优先级 ICR.CCPN。否则请求可以保持待处理，等条件允许后再响应。

响应时，CPU 保存被打断程序的 Upper Context，按 BIV 和 PIPN 找到 ISR 向量入口。向量槽位有 8 字节和 32 字节两种间距，取决于 BIV.VSS 的配置。所以入口地址可以理解为：

硬件实际按对齐后的字段组合生成地址；上式用来理解优先级如何索引向量表。进入 ISR 后，当前优先级会更新，普通中断暂时关闭。ISR 可以按需要重新开放更高优先级中断；执行 RFE 时，进入前的优先级和中断使能状态由保存的上下文恢复。

所以“CAN 已经收到了数据，却没进 ISR”并不等于向量表坏了。先看外设请求是否使能、路由到哪个 Core、配置了什么优先级，再看该 Core 的 ICR.IE/CCPN。这是 Interrupt 独有的一条排查链，Trap 不靠 PIPN 分发。

3. 例子2：保护错误为何直接进 Trap

假设一条 LD.W 读取了当前任务无权读取的区域，触发内存读取保护 Trap。它属于 Class 1，具体原因是 MPR（TIN 2）。硬件按 TCN = 1 找向量入口，再把 TIN = 2 写入 D15。同样在 Class 1 下，写保护和执行保护错误有别的 TIN，却先进入同一个 Class 的向量槽位，由 Handler 继续区分。

Trap 向量槽位固定为 32 字节；当 BTV 按要求配置时，可把入口理解为 BTV + TCN × 32。这里没有 PIPN > CCPN 的判断，也不是先等 ICR.IE 打开。Trap 机制始终有效；响应后会暂时关闭普通中断，但不会把当前 CCPN 改成 Trap Class。

因此只知道“进入了 Class 1 Handler”仍不够，必须看入口处的 D15。一路运行到普通 C 函数后，D15 可能已被后续代码使用；更稳妥的是在 Trap 入口读取，或看 OS 当时保存的 Trap 记录。

保护错误属于同步 Trap，出错位置可以追到这条 LD.W。但 Trap 并不都能这样追：NMI 属于异步 Trap，发生时被打断的指令未必是原因；SYSCALL 则是软件有意执行的系统调用。Trap 与 Interrupt 的区别不是“同步还是异步”，也不是“错误还是正常事件”。

Tricore架构中的不同类别的Trap和定义分类如下：

Trap Class 当前配置 硬件含义
0 UnhandledTrapEntry MMU Trap
1 MemoryTrapEntry Internal Protection Trap，内部保护/内存访问保护异常
2 UnhandledTrapEntry Instruction Trap，指令异常
3 UnhandledTrapEntry Context Management Trap，上下文管理异常
4 UnhandledTrapEntry System Bus Trap，系统总线异常
5 UnhandledTrapEntry Assertion Trap，断言异常
6 SysCallTrapEntry System Call Trap，系统调用异常
7 Core0 为 UserTrapEntry，其他为 UnhandledTrapEntry NMI Trap，非屏蔽中断/SMU Trap

4. 停在 Handler，原来的现场在哪里

TriCore 用 CSA（Context Save Area） 保存上下文。它把寄存器分为 Upper Context 和 Lower Context：进入 Trap 或 Interrupt 时，硬件从 FCX 管理的空闲链取得 CSA，自动保存 Upper Context；PCXI 串起已保存的上下文。Handler 若使用还未保存的 Lower Context，需要遵守相应的保存约定。

Trap 或 Interrupt 刚进入向量入口时，硬件还会改写 A11 作为返回位置。对一般同步 Trap，它指向触发 Trap 的指令；对 SYSCALL、异步 Trap 和 Interrupt，它指向原本接下来要执行的指令。FCD 等特殊 Trap 另有规则。若 Handler 后来执行了 CALL，当前 A11 又会变成函数返回地址；调试器停在深层 OS 函数时，应看入口保存的值或沿 CSA 链还原，不能把此时的 A11 直接当故障 PC。

图中假设入口捕获的 A11 = 0x80012004，反汇编对应一条 LD.W。这只定位到发起访问的指令；被访问的地址还要结合指令操作数、相关寄存器和异常状态判断。若是总线访问类 Trap，还要查该类对应的错误地址与状态寄存器。只看 A11，仍说不出究竟访问了哪里。

在 OS 工程里，实际跳转路径往往是“Class 向量入口 → 汇编入口 → OS HAL Handler → 保护错误处理”。调试器最终停在保护错误处理函数，只说明处理链走到了这里。向前追故障位置，应读 Trap Class、入口保存的 TIN 和返回位置，再结合 CSA 现场；遇到上下文耗尽之类的问题，还要检查 FCX/PCXI 链本身。

5. Cortex-M4 里还有 Trap 和 Interrupt 吗

Interrupt 有，Trap 没有作为与 Interrupt 并列的一套架构入口。Cortex-M4 用 Exception（异常）统称使处理器离开当前执行流的事件：外设 IRQ 是其中一类，HardFault、UsageFault、BusFault、MemManage Fault 是 Fault 类，另有 NMI、SVC、SysTick 等系统异常。这里的“Exception”是总称，并不等于“程序出错”。

这些事件共用一张向量表。表内存的是 Handler 地址，并非 TriCore 那种可执行的向量槽代码。例如 VTOR + 0x0C 放 HardFault_Handler 的地址，VTOR + 0x18 放 UsageFault_Handler 的地址，VTOR + 0x40 开始是外部 IRQ 的 Handler 地址。IRQ 由 NVIC 记录待处理状态并参与优先级仲裁；Fault 按故障类型进入相应 Handler，但同样使用 Exception 的优先级、入栈和返回机制。外部 IRQ 的优先级可配置，HardFault 的优先级固定，高于可配置的 IRQ 和 Fault，低于 NMI 与 Reset。PRIMASK/BASEPRI 能阻止相应的可配置优先级异常，不能按普通 IRQ 的方式挡住 HardFault；FAULTMASK 是另一个会挡住 HardFault 的特殊屏蔽位。

在 Cortex-M4 的后一种情况里，调试器停在 HardFault_Handler，原始原因仍是未定义指令。HFSR.FORCED = 1 表示某个可配置 Fault 升级了，继续读 CFSR 中的 UFSR.UNDEFINSTR 才找到原因；这个例子中，异常栈帧里的 PC 指向那条未定义指令。若 UsageFault Handler 已使能且优先级允许，则会直接进 UsageFault_Handler，根本不经过 HardFault。HardFault 还可能由其他异常处理错误触发，不能把它当作所有“CPU 犯错”的统一名字。

Cortex-M4 进入 Exception 时，在原程序所用的 MSP 或 PSP 上建立基本栈帧，保存 R0–R3、R12、原来的 LR、PC 和 xPSR；Handler 里的 LR 是用于异常返回的 EXC_RETURN，可据此判断该去哪个栈找现场。TriCore 则从空闲 CSA 链取单元，用 PCXI 连接保存的上下文。两边的 Handler 当前 PC 都只是处理代码的位置，不能拿来代替被打断程序的位置。

同一种事件 TriCore 的归类 Cortex-M4 的归类
外设提出服务请求 Interrupt，走 BIV 外部 IRQ，属于 Exception
执行未定义/非法指令 同步 Trap，走 BTV UsageFault；不能处理时可升级为 HardFault
NMI 异步 Trap，走 BTV NMI，属于系统 Exception
主动请求系统服务 SYSCALL 触发 Trap SVC 触发 SVCall Exception

因此 HardFault 不是 TriCore Trap 的一对一对应物。用“非法指令”对比时，TriCore 直接看 Class 和 TIN；Cortex-M4 先看实际进入哪个 Fault Handler，若是 HardFault 再查有没有升级以及原始 Fault 状态。这才是两套机制在调试现场最明显的区别。

6. 调试时先认入口，再找原始现场

TriCore 停在 Trap Handler：先确认 Core 和 Class，查入口保存的 TIN。若是同步 Trap，从入口保存的 A11 回到触发指令，结合反汇编、寄存器和状态寄存器找实际访问目标；若是异步 Trap，A11 只是被打断时的返回位置，不能直接认定那条指令就是原因。

TriCore 外设中断没有进入 ISR：查看外设是否发出服务请求，再查请求使能、目标 Core 和优先级，最后对照 BIV 与 ICR。这里没有“读 D15 找 TIN”这一步。

Cortex-M4 停在 HardFault_Handler：先看 HFSR；若 FORCED 置位，继续看 CFSR 里是哪类 Fault 的状态位。再依据 EXC_RETURN 选择 MSP/PSP，检查异常栈帧里的 PC。例如 UFSR.UNDEFINSTR 指向未定义指令，而非“HardFault 自己产生了一条错误指令”。栈帧损坏或非精确总线错误等情况，还得结合相应状态位解释，不能无条件相信堆栈 PC 就是肇事指令。

TriCore 的 Trap 和 Interrupt 最终都可能用 RFE 返回，但返回动作不会修复故障。同步 Trap 的触发条件如果仍在，返回后可能立刻在同一条指令再次进入 Trap；在 Cortex-M4 上，故障指令未被修正也可能反复进入 Fault Handler。先弄清入口、原因和返回位置，再考虑能否继续执行。
