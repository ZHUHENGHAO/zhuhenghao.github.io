VeriSilicon QEMU 模拟平台调试与 FIFO 排错笔记

写于：2026-06-06

摘要

这篇博客记录了 VeriSilicon QEMU 模拟平台下的 SDK 工程组织、板级初始化、静态库链接、事件系统与 IMU FIFO 调试排错过程。

  • 关于 .init = qemu_board_init,：这是 C99 的“指定初始化器”（designated initializer），用于按成员名初始化结构体。
  • 语法示例：const BoardOperations qemu_board_ops = { .init = qemu_board_init, .find_device = qemu_board_find_device };
  • 含义：把 BoardOperations 类型的结构体 qemu_board_ops 里的 init 成员，赋值为函数 qemu_board_init 的地址。
  • 这是合法标准 C（C99 及以后），GCC / Clang / MSVC 都支持。
  • 比较：也可以用位置初始化，但指定初始化更清晰，也不受成员顺序影响.
  • 关于“把操作表告知平台框架，意义在哪”——直观解释：
  • BoardOperations（见 board.h）是一个函数指针表，类似面向对象里的 vtable / 接口。
  • 它包含 init、find_device 等回调。
  • board_get_ops() 在 bsp/src/qemu_board.c 返回具体板子的 qemu_board_ops。
  • board_register(board_get_ops()) 的作用是：把这张“功能表”交给框架保存起来。
  • 这样框架就能在统一位置调用板级实现，而不用硬编码每个板子的函数。
  • board_init(&board_dev) 的作用是：统一调用已注册的 ops->init(&board_dev) 完成硬件初始化。
  • 它还会把运行时信息，比如 board_dev.name，填入 board_dev。
  • 好处主要有四个：
    • 解耦：框架代码不依赖具体板子实现。
    • 可插拔：同一套框架能管理多种板子。
    • 可模拟：可以替换为 imu_simulator_ops，方便在 QEMU 或单元测试中运行。
    • 生命周期统一：注册阶段负责“谁能做事”，初始化阶段负责“开始做事”。
  • 为什么看起来“只要硬件初始化就行”？
  • 因为硬件初始化确实是必须的。
  • 但注册/操作表提供了工程组织和扩展能力。
  • 如果项目只含单一板子，且实现固定，直接调用初始化也可以。
  • 如果系统支持多个板子、模拟/真实切换或插件式驱动，操作表 + 注册模式会更灵活、更易维护。
  • 源码参考（可查看）：
    • 接口声明：board.h
    • qemu 板实现：qemu_board.c
    • 在 main.c 中的调用流程：board_register(board_get_ops()); → board_init(&board_dev);

QEMU 是什么

QEMU 是一个开源的”虚拟机“软件。它的作用是：在你的 Windows 电脑上，完全模拟一块 RISC-V 芯片的硬件。

打个比方：

  • 你的代码是为”一台不存在的 RISC-V 手机”写的
  • QEMU 就是一个”模拟器手机”，可以在 Windows 上假装运行这台不存在的手机
  • 代码不需要任何修改，直接在这台”假手机”上跑

它本质上就是一个 Eclipse “跑在 QEMU 上”的运行配置，

galaxy_sdk 和 qemu 的关系

如果只跑真实硬件，不需要 qemu/ 整个文件夹。

你只需要 galaxy_sdk/ + 硬件板子的启动文件。

这里说的启动文件，通常包括链接脚本和固件烧录工具。

qemu/ 纯粹是为了在电脑上模拟运行而存在的.

为什么 Nuclei Studio 能显示串口打印

这是 Semihosting（半主机） 机制：

程序并不是把串口数据真的发到硬件 UART 上。

它是通过 QEMU 提供的调试通道，
把输出转给宿主机上的 Nuclei Studio。

所以这里看到的“串口打印”，本质上是模拟器帮你做了转发。

你的代码里调用的 uart_printf()，最终会通过 semihosting 指令通知 QEMU。

这里的 semihosting 是一种 RISC-V 特殊指令。

QEMU 收到后，会把这些数据转发到启动它的父进程，也就是 Nuclei Studio。

Nuclei Studio 再把它们显示在下方的控制台窗口里.

这个过程完全不需要真实的 UART 串口硬件，全部在 QEMU 模拟器内部完成。

.a文件的理解

.a 是 Archive 的缩写，Unix/Linux 下的静态库文件。

类比理解

想象一个打包好的零件箱：

.a 文件 里面装的零件
bsp_riscv.a qemu_board.o、startup.o 等
driver_riscv.a hal_imu.o、imu_simulator_ops 等

每个 .o 文件就是之前编译好的目标文件（二进制机器码）。

链接器怎么用

链接器根据你代码里 extern 的函数名（如 imu_simulator_ops），去 .a 里**找对应的 .o**，把它”拆出来”拼进最终的 qemu.out。

为什么叫”静态”库

因为链接时直接把代码拷贝进最终的二进制里（qemu.out），不依赖外部文件。相对的还有动态库（.dll / .so），程序运行时才加载。

简单总结

.a = 预编译好的二进制代码包。

它的作用是节省重复编译时间，也便于闭源保护。

你链接时可以使用它，但看不到源码。

VeriSilicon 把 IMU 模拟器这样封装起来，就是这个思路.

在QEMU模拟平台上使用dataReady中断从FIFO缓冲区中读取IMU数据时产生的错误：

[IMU] Data-ready interrupt initialized, waiting for data…

好，现在让我把完整逻辑整理清楚。从反汇编里我已经定位到了关键信息，直接给出结论。

错误 vs-imu-sim@intr config error, when read gyro accel data! 原因

从 qemu.lst 反汇编写回 C 代码后，可以发现：

bmi160_fifo_parsing_gyro_accel 在解析 FIFO 前，会先做 6 项影子寄存器校验。

这些值都从地址 s1，也就是 shadow config 区域里读取.

报错原因：如果直接调用 hal_imu_set_accel_cfg / hal_imu_set_gyro_cfg 设置任意参数，
影子寄存器里这些“关键偏移”的值就会不符合 QEMU 硬编码的期望值。

结果就是每帧数据都会触发 intr config error，解析直接失败并返回错误码.

解决方案

main.c 里的 Step 4–5 就是针对性的修复：

两步配合：先拿 QEMU 要求的默认值保证其他字段全部对，再只改 ODR 一个字段。

现在的完整配置流程

FIFO 读取：读哪里？15 帧怎么来的？

FIFO 本身在 QEMU 模拟器内部，不是主存里的数组。

当 hal_imu_read_gyro_accel 被调用时：

  1. QEMU 模拟器的 bmi160_get_fifo_data 从 imu_fifo.byte_counter 读当前字节数
  2. 计算 frame_count = byte_counter / 4（4 字节/帧）
  3. 按 4 字节/帧从 imu_fifo.data[] 复制到 ImuGyroAccelData 数组（memcpy）
  4. byte_counter 清零，释放空间给 timer 继续注入

49 字节 / 4 ≈ 12 帧。

但因为 timer 注入和 CPU 读取之间有时间差，实际 byte_counter 会积压到约 60 字节。

也就是 ≈ 15 帧。

每次进来读一次，就会把 FIFO 里全部积压的数据读走。

所以每次 frame_count 都接近 15。

FIFO 是 QEMU 里一块模拟的环形缓冲区。

timer 每 200ms 往里写 49 字节，也就是 3 帧 gyro + 3 帧 accel。

CPU 没读走就继续积压，满了就报 watermark 中断.
