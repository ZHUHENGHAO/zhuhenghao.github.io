3. VeriHealthi Embedded SDK的Event系统理解和使用

在了解Event的机制之前，首先简单说明一下这个SDK,SDK的全称是software development Kits，中文意思是软件开发工具包。通常是芯片原厂提供的一套开发工具合集，像嵌入式方向提到的SDK常常就是一套包含了底层底层驱动代码、基本的功能函数代码等，可以大致的类比于一个工程模板，模板里写好了所有的底层代码，用户只需要调用需要使用的底层函数初始化，再在上面去编写业务层即可。值得一提的是可能容易产生混淆的概念API，API是应用编程接口，它的概念其实是一种能连接到远端or本地的一种特定格式的接口，也就是说通过特定的规则去调用这个API能够去访问到API另一端的代码去调用。也就是说SDK常常是已经包含了API的，它当然是给用户提供了某些功能的调用接口的，这就是API了。而API在嵌入式里概念常常是远端的，也就是通过这个接口调用的功能块代码并不在我们本地，而是云端，比如说调用一个TTS(语音合成)的API，这个API是由某些公司如百度云智能TTS提供，我们提供ESP系列的模组可以去联网提供调用API去让云端实现功能再返回我们需要的数据。

​ 接下来步入正题，根据VeriHealthi Embedded SDK 开发手册可知：

模块功能：提供各种通用型模块的实现，包括 BLE 服务， Event 系统以及内存管理等模块。
VPI：各个模块功能向上层提供统一的 VPI 接口用来提供服务。这里的VPI按照我个人的理解，应该是跟API的概念差不多，都是一个接口。

Event应该是此SDK提供的一个事件的概念，可以用于任务之间通过事件的触发完成一些通信。
Event基础框架设计

l 一个 task 对应一个 manager

l Manager 可以注册感兴趣的 event， 一个 manager 可以注册多个 event

l Manager 发一个 event，所有注册过该 event 的 manager 都会收到

l 需要在 task 的 while(1) loop 里调用 vpi_event_listen 来监听其他 manager 发来的 event

l 使用 vpi_event_notify 接口给其他 manager 发送 event

说一些我认为比较关键的点：

1. 事件管理器

事件管理器也就是上述提到的manager，一个任务通常应该对应一个任务管理器，通过vpi_event_new_manager来创建一个新的事件管理器，第一个参数是说明这个管理器的类型，可能是用于说明用来管理哪些类型的事件的。第二个参数就是填这个事件管理器需要对应的回调函数，意思是只要manager收到了注册过的事件被触发的消息，就会调用这个回调函数，函数里我们可去做一些事件的判断和处理，比如今天我就做了一个简单的判断事件类型和接收的数据类型并进行打印：

int sys_manager_handler(EventManager manager, EventId event_id, EventParam param)

{

//这是管理器的回调函数，一旦接收到

if (event_id == EVENT_SYS_TEST && param) {

​ uint32_t val = *(uint32_t *)param;

​ uart_printf(“sys_manager_handler received value 0x%lx\r\n”, (unsigned long)val);

​ return EVENT_OK;

}

return EVENT_ERROR;

}

更具体的说明具体如下：

  • vpi_event_new_manager(EventManagerId manager_id, EventHandler handler)

    • 第一个参数 manager_id：管理器的身份/类型（例如 EVENT_MGR_CUSTOM、EVENT_MGR_SYS），用来标识“这是哪个模块/子系统的管理器”。
    • 第二个参数 handler：回调函数指针 EventHandler，当该管理器收到事件时调用。

  • “管理器类型”不是“事件过滤器”。

    • 管理器可以注册任何事件，是否能收到事件只取决于你有没有调用 vpi_event_register(EventId, EventManager)。

2. 事件注册

一个事件被发送了出去，事件管理器能否被触发，主要就靠这个事件管理器是否注册了这个事件以及是否正在监听事件。所以，一个任务想要接收事件并做出反应，需要做的是：创建事件管理器mannager、注册想要监听的事件、监听。

  • [vpi_event_register](vscode-file://vscode-app/f:/Software/VS Code/Microsoft VS Code/034f571df5/resources/app/out/vs/code/electron-browser/workbench/workbench.html) 的原型是 int vpi_event_register(EventId event_id, EventManager manager);
  • 第一个参数 event_id：事件 ID，类型 EventId。你传的 EVENT_SYS_TEST 表示“系统测试事件”这一类事件。
  • 第二个参数 manager：事件管理器句柄，类型 EventManager。你传的 pSysManager 表示“哪个管理器要接收这个事件”。

调用效果：把 EVENT_SYS_TEST 绑定到 pSysManager，以后任何任务调用 vpi_event_notify(EVENT_SYS_TEST, …) 时，事件系统就会把这个事件分发给 pSysManager 对应的回调。

3. 事件事件管理器对应的回调

事件管理器对应的回调，这个在一开始创建事件管理器的时候就提到了要传入一个回调函数的进去，就是用于这个任务中创建的任务管理器被注册的事件触发后，自动调用的。在回调函数中可以做一些判断，比如触发事件的ID、监听数据的类型。

4.1我的理解:

这么说HAL是硬件抽象层，就是直接和硬件寄存器交互的，负责抽象出接口函数，由HAL库写好的函数去操作对应的寄存器，目前我了解到的HAL是由ST公司推出的？可能每个芯片原厂公司都会推出自己的HAL，毕竟HAL的概念就是硬件抽象层，是为了芯片原厂本身的管理和推广以及使用芯片用户的使用感受而产生的。哪个公司退出自己的HAL都是适配于公司内的芯片，不适合其他芯片，因为只有自己公司的芯片手册，根据公司内不同的芯片的寄存器做适配，其实也就是一堆的条件宏，同一个公司的芯片，又有一些统一的寄存器名称和配置，然后不同系列可能会多一些特殊的寄存器，HAL则是公司自行去根据这些去做适配，所以HAL是同一套东西做了各自芯片的冗余，不同芯片都用这一套，只不过会通过条件宏和头文件等方式选择性适配使用的芯片。按我的理解，在汽车电子行业用到的AUTUSAR里，有一个概念叫做MCAL层，也就是Miro Controller Abstraction Layer，其实跟这个HAL的概念很类似，但是MCAL是能适配各种芯片厂商的芯片的，我的理解就是MCAL相当于各家芯片厂商的HAL的集成。BSP则是为了适应不同板子的一个软件层级，同一个公司不同系列的芯片引脚数不一样，具体的资源也不一样，而BSP则是针对某个系列的板子而适配的板级支持包，一般不同系列的板级支持包是分开的，这个BSP层投射出来的效果就是板级层面的，例如由BSP层具体硬件资源的对应，如某一系列的芯片A1-A6引脚可以配置成ADC进行采集，还有别的吗，我想不到了你补充一下。以上两层多少还是和硬件交互比较深，至于驱动层则是在此之上更接近纯粹的软件层面，只需要拿到前两层抽象出来的接口去配置某些外设的具体功能，这些叫控制器驱动，之所以叫驱动就是因为在用户的视角和体感上，是自己使用或修改这个驱动层去完成具体功能的配置，实则是人和驱动层交互，驱动层下面跟BSP、HAL交互最终配置到芯片寄存器。而设备驱动则是稍微比控制器驱动高半个层级的概念，控制器驱动在用户视角是想要设置好芯片的某项内置功能，而设备驱动则是用户想要用这个芯片控制、接收某个连接到芯片或板子的新设备，这就涉及到两件事了，第一依旧要对芯片芯片进行配置以此达到引出一个芯片端对接入设备的交互接口的目的。第二，在此基础上要根据接入设备的特性和原理(比如通信协议、设备通信可接收的速率等)写一个类似”接入设备的通信层”，以此输出一个接口提供到应用层，可由应用层调用这个接口完成业务上的逻辑代码。那SDK就是HAL、BSP、驱动、简单的App层demo构成的整个包吗，也就是所谓的软件开发工具包。 以上就是我的理解，哪里不对或者缺失的，请你补充。

一、HAL层：你的理解基本全对，补充2处细节+修正1个小偏差

正确部分（全部认同）

  1. 各芯片原厂自研专属HAL，直操作寄存器、封装原子级硬件API，原厂HAL只适配自家SOC，跨厂不能通用；
  2. ST HAL、NXP MCUX、瑞萨FSP均是原厂基于自家芯片寄存器手册开发，同品牌多型号靠头文件+条件宏做代码裁剪复用，一套源码适配全系是主流设计思路；
  3. HAL只关心芯片内核/片内外设寄存器定义，完全不关心PCB布线、引脚外接什么器件，和板级无关。

修正+补充缺失内容

  1. 小偏差：不是所有原厂HAL都靠「单套源码+宏冗余」实现全系列适配
    ST HAL是单源码+芯片选型头文件宏裁剪，但TI、Microchip部分MCU HAL采用分系列独立源码，同品牌不同产品线分开维护，不用一套源码堆宏；
  2. 关键遗漏：ARM推出跨厂商标准抽象：CMSIS
    所有Cortex-M内核芯片（ST/NXP/瑞萨）原厂HAL强制兼容CMSIS规范，ARM统一规定SPI/UART/ADC标准函数原型；CMSIS是脱离芯片厂商的通用硬件抽象，相当于行业通用版迷你HAL，用来统一不同原厂HAL的上层调用接口，是裸机跨芯片移植的基础，你没有提到这个行业通用规范。

二、MCAL(AUTOSAR)：【你最大核心误区：MCAL≠各家HAL的集成打包】

错误原文：MCAL是各家厂商HAL集成、能适配多种芯片❌，这条必须重点纠正，是车载AUTOSAR最容易踩的坑
正确MCAL逻辑

  1. MCAL是【接口标准规范】，不是HAL合集
    AUTOSAR联盟统一制定MCAL上层API标准（比如Dio_WriteChannel()、Spi_Transmit()、Adc_GetValue()全全球统一函数名、入参）；
    芯片厂商（英飞凌/瑞萨/NXP）基于自家原厂HAL，去实现这套标准化API。
    分层链路：
    AUTOSAR上层BSW（COM/OS/ECU配置）→ MCAL标准API(统一规范) → 厂商实现层(调用自家HAL) → SOC寄存器
  2. 单个项目MCAL仍然绑定一款SOC，不能一个MCAL包同时跑英飞凌TC397+NXP S32K；
    换芯片只需要替换「MCAL底层实现包」，上层AUTOSAR软件完全不用修改，这才是MCAL跨芯片解耦的本质。
  3. 补充：MCAL模块和原厂HAL一一对应：DIO/PORT对应GPIO HAL、ADC对应ADC HAL、CAN对应CAN控制器HAL；AUTOSAR里PORT模块的引脚配置功能 = 裸机BSP的引脚定义。

类比帮你理解

  • HAL=各品牌手机底层驱动（华为驱动、小米驱动）；
  • MCAL=安卓系统统一硬件接口标准；
  • 厂商MCAL实现=华为/小米按照安卓标准封装自家底层驱动，安卓APP不用改就能在不同手机运行。

三、BSP层：你的理解方向正确，仅只列举了引脚→ADC映射，大幅补充BSP全场景工作内容（工业/车载/Linux通用）

你原文：BSP只做引脚资源映射（A1~A6配置ADC），除此之外BSP完整职责分6大类：

  1. 时钟域配置：板载外部晶振（8M/24M/40M PCB硬件决定）、PLL倍频系数、各外设时钟分频；同芯片换板子晶振不一样，BSP必须修改，HAL只提供时钟配置函数，不写死晶振参数；
  2. 电源域配置：板上外设供电引脚、IO域电源开关、外挂芯片（LCD、传感器）上电时序，由PCB硬件设计决定；
  3. 中断资源分配：片内外设中断优先级、外部中断绑定引脚、中断向量板级分配；
  4. 总线片选与硬件引脚功能：SPI_CS、I2C复位脚、LCD背光脚、BOOT启动配置引脚（ARM芯片启动方式由硬件BOOT脚决定，属于BSP）；
  5. 内存硬件映射：片外SDRAM、QSPI Flash、NorFlash的物理地址、分区大小、硬件启动地址（Linux设备树DTS核心内容）；
  6. 板级硬件补丁：弥补PCB硬件缺陷，例如原理图UART_TX没接上拉电阻，芯片手册不需要上拉，但硬件必须开启，该配置写在BSP，HAL无相关配置。

补充小知识点：

  1. Linux内核中设备树DTS = Linux标准化BSP，裸机是bsp_xxx.c文件，AUTOSAR中ECUC配置工具生成的资源配置 = AUTOSAR版BSP；
  2. 现代规范BSP严禁直接操作寄存器，所有初始化全部调用HAL接口；老式裸机直接寄存器写BSP是历史遗留不规范写法。

四、驱动分层（控制器驱动/设备驱动）：你的理解100%精准，仅补充边界特例

你的核心观点全部正确：

  1. 控制器驱动：面向芯片内置控制器（UART/SPI/CAN/ADC硬件控制器），基于HAL+BSP封装零散原子API，实现多字节收发、环形缓冲、DMA中断等完整控制器功能，面向芯片内置硬件；
  2. 设备驱动：依托控制器驱动打开硬件总线接口，再按照外接器件通信协议（W25Q指令、LCD8080时序、GPS NMEA协议）封装外设操作接口，对接板载外挂器件，向上暴露应用API。

补充3个边界细节

  1. 特例：片上外设也会衍生设备驱动
    CAN控制器是芯片内置→控制器驱动；CAN总线外挂TJA1050收发器（板上硬件）由BSP配置，CAN报文DBC解析、协议封装属于上层设备驱动；
  2. 分层目的落地：硬件变更影响范围
  • PCB改LED引脚：只改BSP，HAL、LED驱动代码不动；
  • 更换W25Q为GD25Q：只修改W25Q设备驱动，SPI控制器驱动、BSP片选引脚不变；
  • 更换主控芯片：替换原厂HAL+全量BSP，上层控制器/设备驱动仅少量适配（靠CMSIS/MCAL标准化）；
  1. Linux分层对应：platform_driver=片上控制器驱动，spi/i2c设备驱动=外挂器件驱动。

五、补充你整套逻辑缺失的2个宏观知识点

1. 分层设计的终极目的（你没总结）

HAL屏蔽芯片寄存器差异、BSP屏蔽PCB硬件差异、驱动屏蔽器件协议差异；分层隔离后，上层应用完全脱离底层硬件细节，硬件改版不动业务代码。

2. 特殊无HAL场景

老旧8位MCU(51/AVR)无原厂HAL库，没有抽象层，BSP和驱动直接裸写寄存器，是无分层特例。

六、精简层级汇总（对齐你的理解）

AUTOSAR等效替换：MCAL标准接口=通用HAL规范，ECUC配置=BSP，CDD驱动=设备驱动。

七、SDK说明

SDK = 整套芯片开发软件包 ≠ 只包含 HAL+BSP + 驱动 + Demo，HAL/BSP/ 板级驱动 / 示例工程是 SDK核心主体，SDK 还附带大量配套组件、工具、中间件。

一、标准原厂 MCU SDK 完整组成（以 STM32CubeSDK、NXP MCUXpresso SDK、瑞萨 FSP 为例）

1. 底层硬件层（你提到的部分）

  1. HAL/LL 库：芯片寄存器抽象，原厂硬件接口（最底层）
  2. 板级 BSP：官方评估板 (EVB / 开发板) 专用引脚、时钟、硬件初始化配置，原厂只配套自家官方样板的 BSP；用户自制 PCB 需要自己基于 HAL 重新编写 BSP
  3. 片上控制器驱动：UART/SPI/ADC/CAN 等片内外设封装驱动
  4. 板载外设设备驱动：原厂开发板搭载的 W25Q、LCD、按键、传感器、以太网芯片驱动

最后，经过了解，其实各个厂商实现的架构都略有不同，比如对于HAL的概念，芯原的做法是放在App和驱动中间进行解耦的:

图里是芯原自研架构的 HAL（设备接口抽象型 HAL），和 ST、NXP 这类通用 MCU 原厂寄存器封装型 HAL是两种完全不同的落地思路，只是共用「HAL 硬件抽象层」这个名词。

一、两种 HAL 核心架构对比（对应你之前学的 ST HAL + 本图芯原 HAL）

1）ST / 通用 MCU（Cortex-M 原厂：ST、NXP、瑞萨、AUTOSAR MCAL）：【寄存器抽象 HAL，在驱动下方、紧贴硬件】

分层：硬件寄存器 → HAL（寄存器封装 API）→ BSP → 设备驱动 → APP

  • HAL 抽象对象：芯片 SOC 寄存器，把零散寄存器读写封装成原子函数；
  • 驱动调用 HAL 接口实现功能，HAL 永远在驱动底层。

2）芯原图中架构（ASIC/ISP/IP 平台常用：芯原、部分自研 RTOS）：【设备接口抽象 HAL，夹在 APP 和驱动中间】

分层（和图纸完全匹配）：APP → HAL（统一接口 + 函数指针调度层）→ Device 驱动 → BSP / 寄存器

  • HAL 抽象对象：各类外设驱动的接口规范，不碰寄存器；
  • HAL 只做三件事（图纸标注）：
    1. 提供一套全设备通用的统一 API（Dev_Open/Dev_Read/Dev_Write）；
    2. 驱动初始化时向 HAL 注册自身的函数指针（ops 操作集）；
    3. APP 调用 HAL 接口，HAL 根据设备 ID 查找已注册的函数指针，跳转执行对应驱动代码。

本质：芯原这套 HAL = Linux 内核里的VFS 虚拟文件系统（VFS 在应用和具体文件系统驱动中间，靠file_operations函数指针注册分发，逻辑 1:1 复刻本图）。

二、为什么都叫 HAL，但分层截然相反？

HAL 仅为概念：Hardware Abstraction Layer（硬件抽象层），只约束「做硬件抽象」，不约束抽象哪一层硬件

  1. MCU 厂商抽象【芯片硬件】：要屏蔽寄存器差异 → HAL 贴寄存器；
  2. 芯原（IP/ASIC 厂商）抽象【外设驱动】：要屏蔽不同设备驱动接口差异 → HAL 夹在应用与驱动之间，统一上层调用。

图纸关键设计解读（对应图上文字）

  1. 驱动和 APP 解耦：APP 全程只调用 HAL 标准接口，不需要包含任何驱动头文件、不用关心底层是 DeviceA 还是 DeviceB；
  2. 驱动注册绑定 HAL：每个驱动启动时，把自己的open/read/write函数地址填入 HAL 全局设备表；
  3. HAL 层极薄：自身没有硬件操作代码，只做参数校验 + 函数指针跳转，无具体硬件逻辑，和图中 “HAL 层非常薄，简单理解就是函数指针的调用” 描述一致。

三、补充 BSP 在芯原架构里的位置

芯原架构中，BSP 被收拢在 Device Driver 内部：

Device 驱动 = 原 ST 架构的「BSP（板级引脚 / 时钟配置）+ 寄存器操作代码」，驱动包揽硬件适配，HAL 不再参与硬件配置。

四、快速一句话区分

  • ST-HAL：向下抽象硬件寄存器（靠下、近硬件）
  • 芯原 - HAL：向上抽象驱动接口（居中、夹在应用驱动中间）

行业规律：通用 MCU 多用 ST 式 HAL；ASIC、图像处理 ISP、自研 SoC 芯片（芯原这类 IP 公司）普遍采用图纸里芯原式 HAL 架构。
