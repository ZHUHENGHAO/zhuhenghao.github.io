编译构建链路的详细理解

写于：2026-06-14

摘要

以前对编译构建的底层链路不熟悉，只停留在了解gcc和makefile的层面上，自己最常使用的编译也是IDE里封装好的图形化编译按钮，一键编译、烧录。最近在公司的接触到这方面的任务，详细的理解了一下实际大型项目里的整套交叉编译工具链和原理，我觉得很有帮助，特此记录一下。真实的大型项目开发场景里，常常并不会有完整的一套IDE给你让你一键编译，而是用命令行去调用工具链编译，中间还需要写编译构建的规则文件，实现灵活配置。像是这个项目，我第一次编译就用了50分钟，这还是使用了ninja并行编译的情况下。

大型项目里可能会涉及到很多的编译前配置，比如可能会需要根据项目的具体场景给内存划分好不同的flash分区(BM、BL、APP、UCB等)甚至ram分区，尤其是涉及到多核的芯片，每个核都会有单独的也有共享的内存空间，编译后的.o文件会声明这个对应的.c文件内容里分配到的不同的段(比如默认的代码段(.text)、(只读数据段).rodata、.data、.bss段还有自定义的段，比如.SW_VERSION_STRING，用来专门存储版本号变量的段)。在.c到.o的过程中，把每个c的各个内容分配到了不同的段里面，每个.o都有相同的默认的段，也有其特有特殊定义的段，但此时还没有把这些段映射到真实的物理地址上，那么ld文件就派上用场了，在这个文件里就是专门去灵活的配置各个段映射到的真实物理地址上去的，做完这一步以后才能真正的生成可执行文件，让你项目的代码的所有内容具体的分配到芯片真实的物理地址上去，芯片以它设计好的规则去运行，才能够完整的去执行你的程序。具体的梳理，将在文章下详细的解释。

编译构建链路是嵌入式开发中最核心的底层基础设施之一，理解其完整流程对于掌握固件从源码到可执行文件的每一步转化至关重要。本文以 AURIX TC397x 项目为实践载体，梳理了 CMake、CMakeLists.txt、Ninja 与 GHS 编译器/链接器各组件的核心概念，再通过编译链路序列图深入分析了构建配置、并行编译、归档、链接四阶段的完整时序；随后解析了项目五层构建命令传参链路（Build.bat → Python → CMake → Ninja → GHS），最后深入分析了链接脚本（LD 文件）的 MEMORY 与 SECTIONS 两大核心块的结构与作用，以及编译产物 MAP 文件四个分区的内容含义与实际应用场景。掌握这些内容，是进行固件体积分析、内存越界排查、二进制数据提取等工程实践的基础。

关键词：编译链路、链接脚本、LD 文件、MAP 文件、嵌入式工具链

1. 编译链路全景

1.1 核心工具链组件概念

在探讨编译流程之前，应该大致了解一下过程中涉及到的工具链和概念，先梳理本项目涉及的几个关键工具及其各自作用，理解它们在链路中的位置与职责。

CMake：一个跨平台的构建配置工具。传统 Makefile 需要手动逐条编写编译命令，而 CMake 采用声明式语法（CMakeLists.txt）描述”目标（Target）及其依赖关系”，再由 CMake 自动生成与平台对应的底层构建文件（比如 Makefile，但本项目为 build.ninja，用于ninja这个构建工具快速的解析并行调用编译器）。这种解耦使得项目可以同时支持多种工具链，只需要切换 CMake 工具链文件即可。

CMakeLists.txt：CMake 的主配置文件。以 add_executable(hello main.c utils.c) 为例，声明了”构建一个名为 hello 的可执行文件，它依赖 main.c 和 utils.c”这一目标，CMake 解析后自动推导出编译顺序与规则。项目中还通过 -DBUILD_SW=APP 等变量传递编译分区类型等关键参数。

.cmake（CMake 模块文件）：.cmake 文件是 CMake 的可复用模块文件，起到*”include 公共片段”**的作用，有点像c语言里的头文件——将跨项目共享的路径变量、编译选项、工具链路径等抽离为独立文件，供多个 CMakeLists.txt 统一引用。在本项目中，Aurix-toolchain.txt 就是一个 .cmake 工具链文件，它通过 CMAKE_TOOLCHAIN_FILE 机制在 CMake 配置阶段优先加载，向 CMake 提供 GHS 编译器的路径（/opt/ghs/comp_202248/）、目标架构（TriCore TC397x）以及交叉编译必需的系统根目录等关键信息。CMake 在配置阶段读取工具链文件后，才会在后续解析 CMakeLists.txt 时正确调用 GHS 编译器而非默认的本地 GCC。

Ninja：一个专注于执行速度的构建系统，和make是一个层级的工具。但是相比 GNU Make 逐条解析 Makefile 的串行方式，Ninja 基于 CMake 生成的build.ninja(编译规则文件)，相当于手写的makefile文件，里面定义了”使用什么编译器？编译哪些文件？链接哪些文件？的具体规则”，进行高并发调度，所有无依赖关系的编译任务可同时并行执行，大幅缩短增量编译时间。

GHS 编译器（cctri/cxtri）与链接器（elxr）：Green Hills Software 专为 TriCore/AURIX 架构提供的商业级交叉编译工具链，和GCC编译器是一个层级的工具。编译器将 .c 源码编译为 .o 目标文件，链接器（elxr）负责将全部 .o 文件及静态库按链接脚本分配的地址整合为最终固件，并输出 .out（调试用 ELF 格式）、.map（地址映射表）和 .s19（烧录用格式）。

1.2 编译链路时序解析

了解了各工具的作用后，本节按时间顺序梳理编译链路从配置到产出的完整过程。

第一步：构建配置（CMake 读取 CMakeLists.txt 生成 build.ninja）

开发者执行 Build.bat 后，Python 脚本解析参数并调用 CMake。CMake 加载项目根目录下的 CMakeLists.txt（主配置文件）以及通过 -DCMAKE_TOOLCHAIN_FILE=Aurix-toolchain.txt 指定的工具链文件。CMake 遍历源码目录结构，解析各 CMakeLists.txt 中声明的目标及其依赖关系，最终自动生成 build.ninja——一份包含”使用什么编译器、编译哪些文件、链接哪些文件”的完整构建规则文件。

第二步：并行编译（源文件 → 目标文件）

Ninja 读取 build.ninja 后，为每个 .c 源文件生成一条编译命令，由 GHS 编译器（cctri/cxtri）并行执行：

  • 编译器对每个 .c 文件进行语法检查和语义分析，将错误和警告信息反馈回源文件供开发者修正。
  • 解析 #include 的所有头文件（.h），确认其中的函数声明、结构体定义与实际实现是否一致。
  • 编译完成后输出 .o 目标文件（ELF 目标格式），包含机器码和未解析的符号引用。

第三步：归档（目标文件 → 静态库）

对于需要封装为库的功能模块，GHS 归档工具（ar）将多个 .o 目标文件打包为 .a 静态库，便于其他模块统一引用，省去逐个 .o 管理的繁琐。

第四步：链接（静态库/目标文件 → 可执行文件）

Ninja 最后执行一步链接命令：GHS 链接器（elxr）将所有 .o 目标文件和静态库（.a）合并，按 LD 链接脚本分配的地址整合为最终固件，输出 .out（ELF 调试映像）、.map（地址映射表）和 .s19（烧录用格式）。

2. LD 文件（链接脚本）理解

2.1 LD 文件的作用

LD 文件（Linker Script，链接脚本）是编译前由开发者手写的配置文件，核心作用是定义固件中每个代码段和数据段在 Flash/RAM 中的绝对物理地址。开发者需要根据芯片硬件手册中的内存映射表来编写 LD 文件，通过 MEMORY {} 块声明每个区域的起始地址和大小，再通过 SECTIONS {} 块将编译器生成的段（如 .text、.rodata、.bss）映射到对应的物理区域中。

项目 LD 文件结构图展示了嵌入式软件开发从需求分析到联调的完整生命周期，以及 LD 文件在其中所处的构建环节位置。

2.2 MEMORY 块：地址空间声明表

MEMORY {} 块是 LD 文件中的地址空间声明表，用于定义一个命名区域的起始地址与大小。实际项目中，MEMORY 声明主要分为三类：

类型 说明 示例
硬件约束 芯片手册强制规定的地址范围，开发者不可更改 TC397 pflash 地址固定为 0x80000000（cached）/ 0xA0000000（non-cached）
架构划分 架构师基于系统需求对物理地址空间的人为逻辑分割 将 pflash 划分为 BM 区、BL 区、APP 区等
保护区占型 声明但不映射代码，防止越界访问 APP 区链接脚本的 MEMORY 中声明其他区地址范围，作用是边界保护

2.3 SECTIONS 块：段映射规则表

SECTIONS {} 块是 LD 文件中的段映射规则表，用于定义编译器产出的各类段分别放入 MEMORY 中哪个地址区域。主要分为三类：

1. 标准段映射：编译器默认生成的段（如 .text、.data、.bss、.rodata）按规则自动归入对应区域，无需显式声明，链接器会依据默认约定处理。

3. MAP 文件（链接映射表）的理解

3.1 MAP 文件的作用

MAP 文件是编译过程中由链接器自动生成的输出文件，完整记录了链接后每个段和每个符号在内存中的最终地址、占用大小以及所属的目标文件。MAP 文件使得不需要源代码也能反向查证固件中任意符号或变量的存放地址，是分析固件体积（RAM/Flash 占用率）、排查内存越界或重叠问题、以及从 .s19/.hex 二进制文件中提取版本号等关键数据的重要依据。

3.2 MAP 文件四大分区解析

MAP 文件整体分为四个功能分区，各有不同的分析价值：

分区 内容 分析价值
① Image Summary（段摘要） 每个段的名称、基址、十六进制大小、十进制大小 分析固件 RAM/Flash 占用率，检查各分区体积是否超出预期
② Module Summary（模块摘要） 每个段来自哪个 .o 文件，以及该文件的调试信息段（.debug_abbrev、.debug_str 等） 追溯某个段来自哪个源文件，定位体积异常的文件
③ Global Symbols（全局符号表） 所有全局符号（函数名、变量名）按地址排序，每个符号的地址和大小 查找变量/函数的最终地址，验证链接脚本分配是否符合预期
④ Global Cross Reference（全局交叉引用） 每个符号在哪里定义、被哪些其他 .o 引用，以及引用的地址 分析模块间依赖关系，排查未定义符号或重复定义错误

3.3 版本号提取的工程实践

一个典型的工程应用场景是：从编译出的固件二进制中直接读取版本号字符串，而无需源代码参与。具体做法是：

  1. 定义阶段：在源码中通过 #pragma ghs section rodata = ".SW_VERSION_STRING" 将版本号放入特殊命名的段。
  2. 映射阶段：在 LD 文件的 SECTIONS 块中，将 .SW_VERSION_STRING 映射到 Flash 中的固定物理地址（如 0xA0094100）。
  3. 读取阶段：固件烧录后，直接从 MAP 文件的 Image Summary 或 Global Symbols 中查得 SW_VERSION_STRING 所在地址。例如 VCUPLUS 的 GM_IDC_VCUPLUS_BL.map 中可直接查到 SW_VERSION_STRING 位于 0xA0094100，用此地址在 .s19 文件中偏移读取即为版本号字符串。

这个机制在生产环境中尤为重要：即使源代码不可得，只要手握 MAP 文件和固件，就能定位并提取任意已知符号的数据。

4. 总结

本文围绕嵌入式编译构建链路展开：首先梳理了 CMake、CMakeLists.txt、.cmake 工具链文件、Ninja 与 GHS 编译器/链接器各组件的核心概念与作用，明确了各层工具的职责边界；随后按时间顺序解析了构建配置、并行编译、归档、链接四阶段的完整时序，并通过项目五层传参链路（Build.bat → Python → CMake → Ninja → GHS）串联起完整的工具协作关系；在此基础上深入分析了 LD 文件中 MEMORY 地址声明与 SECTIONS 段映射两大核心机制，以及 MAP 文件四个分区的内容含义与典型工程应用场景。

理解编译链路各环节的原理，不仅仅是调试固件的基础，更是进行内存优化、固件体积控制以及二进制可观测性工作的前提，对嵌入式开发设计时的理念有很大的帮助。
