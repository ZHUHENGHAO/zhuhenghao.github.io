VeriHealthi 可穿戴健康监测——一个嵌入式系统的完整复盘

写于：2026-07-29

摘要

​ 2026 年 7.19-25，我们参加了芯原杯嵌入式软件开发大赛决赛，这次经历还是比较难忘的，最终其实完成效果还可以，可惜最后因为种种原因没能拿到好名次。。。。

​ 本文是 “芯原杯全国嵌入式软件开发大赛” 参赛项目 VeriHealthi 的复盘记录。我们在 VeriSilicon CocoPalmR 平台上，以 FreeRTOS 为内核、BMI160 六轴 IMU 为数据源，做了一套可穿戴健康监测固件：穿戴检测、手势识别、步态识别在端侧实时推理，结果经 BLE 打包推送手机 App，并打通 UTC 授时、看门狗故障注入、断连缓存重发等可靠性链路。

​ 相比罗列功能，这篇文章主要相讲 设计背后的取舍：为什么用多任务 + 消息队列而不是裸机轮询、为什么 ISR 里 “只唤醒不干活”、穿戴检测为什么必须去 DC、BLE 传输为什么要做 AIMD 自适应批量、算法模型是怎么以 “零 malloc” 的方式塞进单片机的。

注：本博客由完成的项目代码、PPT、报告等喂给 deepseek 完成撰写，本人 review 和修正补充完成。

第一章：我们在做什么

1. 起点：一块 “什么都有” 的开发板

大赛给了一套基于 VeriSilicon Pegasus SoC（RISC-V 架构）的 CocoPalmR 开发板与 SDK。板上的核心资源：

资源 配置 说明
BMI160 I2C1，地址 0x68，50Hz，FIFO 六轴 IMU，带硬件 FIFO
RTC / WDT / GPIO / LED — 时间基准、可靠性、人机反馈
BLE Zephyr 协议栈（libble.a） 与手机 App 通信的唯一出口

SDK 已经把 HAL 驱动（hal_imu、hal_gpio、hal_wdt…）、OSAL（FreeRTOS 的抽象层）、BLE API 都封装好了。所以我们的任务不是从零造轮子，而是 基于这套 SDK 设计出一套有算法、有交互、有可靠性闭环的端侧方案，并让两个方向都能闭环：

  • 数据 → 结果：IMU 原始数据 → 算法推理 → 动作枚举 → BLE 推送到手机。
  • 指令 → 现象：App 写 UTC 授时 → 设备 RTC 生效；App 写故障注入 → 看门狗超时复位。

2. 这套系统最终长什么样

图：五层架构总览 —— 硬件 / HAL / 中间件 / 公共服务 / 应用任务，每一层只通过定义好的接口与上下层打交道。

一句话概括我们的设计主线：同源数据、独立状态、统一事件、可靠交付。

  • 同源数据：所有功能消费同一份 50Hz 六轴数据流。
  • 独立状态：穿戴检测、手势、步态各自维护自己的状态机，互不干扰。
  • 统一事件：识别结果统一映射为 algo_result_t 枚举，协议层与算法解耦。
  • 可靠交付：结果带 UTC 时间戳、递增序号、CRC-8，断连可缓存重发。

第二章：架构设计——先想清楚再写代码

软件设计最基本也是最重要的一环是架构。一个解耦良好的架构，对后续功能与算法的增、删、改都是事半功倍的——这是我们在项目里最深的体会。

1. 为什么是多任务，而不是一个死循环

早期我们评估过裸机 while 循环轮询的写法：把所有外设轮询、算法推理、BLE 发送塞进一个循环。但随着功能增多，这种写法有三个致命问题：一个模块卡住全系统卡住、无法并行开发、实时性无法保障。

最终选择 FreeRTOS 多任务 + 消息队列，每个功能一个独立任务。这不仅是一个技术决策，更是一个 工程组织决策：三人各负责一个或几个任务，接口在公共头文件（wd_queue.h、algorithm_queue.h、result_bus.h、ble_services.h）里提前冻结，可以并行开发、独立调试，互不阻塞。

图：系统数据链路——IMU 采集作为单一数据源，向穿戴检测与算法两个消费者扇出。

2. 任务划分与优先级：数据采集优先

任务 栈(words) 优先级 职责
imu_validation 1024 4 FIFO 采集、样本分发（数据源头）
wdt_monitor 768 4 周期喂狗、故障注入（保命）
wear_detect 512 3 穿戴检测、LED、BLE Notify
algorithm 1024 3 手势 + 步态推理
ble_task 1024 3 打包、连接管理、发送
time_sync 512 3 RTC 授时与同步状态
init_app 512 1 一次性初始化，完成后自杀

优先级设计上我们遵循一条原则：数据采集优先。

  • IMU 任务优先级最高——FIFO 读晚了会溢出丢数据，而数据是一切算法的前提。
  • WDT 任务同优先级——看门狗喂晚了直接复位，属于 “保命” 优先级。
  • 业务逻辑任务放 3，采集空闲时运行即可。

init_app 是个一次性任务，做完外设初始化后 osal_delete_task(NULL) 自我销毁，把 512 words 栈空间还给系统——这个细节被我们沿用到了所有 “一次性” 场景。

3. 公共服务层：五件解耦的 “基础设施”

架构图上有一层容易被忽略但价值最高的部分——公共服务层。它不实现业务，但让业务之间能干净地通信：

模块 作用 典型使用
Queue 连续数据分发 IMU → 穿戴 / 算法两条队列
Result Bus 识别结果统一出口，自动维护递增序号 算法 → BLE 的缓冲队列（深度 256）
VPI Event 控制类事件唤醒 BLE 传输请求、WDT 故障注入
BLE Services 3 个 GATT 服务集中定义 回调注册模式解耦协议层与业务层
Resource Stats 资源监控 队列收发、算法耗时、堆栈统计

这里的关键设计是 Result Bus 承担 “结果总线” 角色：算法任务只负责 result_bus_publish(ts, result)，完全不关心 BLE 是否连着、链路是否通畅。谁消费、怎么消费，由消费者决定。这让算法侧逻辑极其干净，也让断连缓存、重连补发这类可靠性逻辑可以独立在 BLE 侧实现。

第三章：数据链路怎么落地

1. IMU 采集：ISR 只唤醒，不干活

这是我们在嵌入式实时性上最重要的一个决策。IMU 数据 50Hz 产生，FIFO 水印中断触发采集。

ISR 不读 I2C、不打印、不做任何重活，只累加计数并释放信号量；真正的 FIFO 批量读取放到任务上下文：

为什么要这样？ 如果在 ISR 里直接读 I2C，一次 I2C 事务可能占用几十微秒，水印中断又来得快，极易造成中断重载、饿死业务任务。改成 “中断唤醒 + 任务读取” 后，采集吞吐与算法推理互不阻塞，且无论后面加多少消费者，采集侧代码一行不用改——新消费者只需订阅队列即可。

图：IMU 采集任务的 FIFO 中断 → 批量读取 → 双队列非阻塞分发。

2. 穿戴检测：一个 “直觉方案失败后” 的典型复盘

穿戴检测的目标很简单：判断设备是否戴在手上。最直觉的方案是 直接算三轴加速度方差——运动时有波动，静止时没有。

但这个方案一实测就翻车：重力信号主导了方差。佩戴静止时重力分量远大于生理微动，方差和 “平放桌面” 几乎没差别，根本分不开。

复盘结论：先减掉 DC 分量，再做统计。

EMA 低通只跟踪重力的 缓慢姿态变化，步态/手势这类 5~10Hz 的快速运动被大幅衰减，因此基线不会被瞬时动作带偏。去 DC 后的 var 三个量级清晰可分：

场景 var 量级
平放桌面 200 ~ 1000（本底噪声）
佩戴静止 5k ~ 20k（生理微动）
佩戴运动 1,000,000+

阈值判定再用一个 不对称迟滞状态机：上阈值 10000（未戴 → 已戴，立即翻转），下阈值 2000（已戴 → 未戴，需持续 3 秒）。不对称是刻意的——戴上一瞬间要快速响应，而静坐、睡眠这类短暂静止不能被误判成脱落。

图：穿戴检测的阈值判据与状态机。

3. 时间同步：宁可丢数据，不可发错时间戳

设备本身没有绝对时间，所有算法结果都要带 UTC 时间戳，只能靠 App 授时。我们在 BLE 的 Timing Service 上实现了一层 双重授时门控：

授时门控是 双重的——算法侧在 publish_if_synced() 里检查未同步就静默丢弃；BLE 发送侧也要求 “当前连接已授时” 才允许发包。

这是一个我们反复权衡后定下的原则：宁可丢数据，绝不发错时间戳。因为时间戳是后续数据对账、步态节奏分析的基础，错的时间戳比没有更糟糕——它会让整段数据在时间轴上失真。

第四章：BLE 通信——端侧系统的出口

1. 协议设计：轻量、自校验、可追踪

算法结果统一打包成 VESC 协议包发送：

每个 result_item 11 字节：timestamp_ms[8] | sequence[2] | result[1]，全部小端。CRC-8/SMBus 用查表法（多项式 0x07），只校验结果区，避免包头被校验连累。

三个细节体现了 “可追踪” 的设计思路：

  • 递增序号 由 Result Bus 自动维护：设备复位归零、断线期间不归零，保证整段时间序列连续，App 可以据此发现丢包。
  • start_flag 双 bit：bit0 系统首包、bit1 连接首包——让 App 知道 “这批是积压的旧数据补发” 还是 “实时的首包”。
  • 结果枚举 从手势/步态统一映射：捏合 = 2、握拳 = 4、抬腕 = 6、走路 = 8、跑步 = 9…，无效动作直接不发送，减少无效流量。

2. 断连缓存重发：结果一个都不能丢

BLE 连接是极不稳定的——手一抬、走两步就断。算法任务可不管这些，它每秒都在产结果。如果断线期间不处理，结果就全丢了。

我们的方案是 Result Bus（深度 256 的队列）+ BLE 侧断连重发：

256 深度 × 14B ≈ 3.5KB，按 1Hz 输出可缓存约 4 分钟——足以覆盖大多数临时断线场景。重连后 App 拿到的是连续序号 + 连接首包标记，可以完整还原断线期间的动作轨迹。

图：断连缓存重发的整体流程。

3. 自适应批量：把 AIMD 用到了 BLE 上

发结果时单条一条发太浪费——每个 Notify 都有 ATT 头部开销。所以我们在 MTU 允许范围内 批量打包（设计 MTU 515 → 每包最多 45 项）。但问题是：不同连接的链路质量天差地别，固定批量要么塞不满、要么把协议栈内部缓冲打爆。

借鉴 TCP 的 AIMD（加性增/乘性减）：

  • 每次成功发送后批量上限 +1（试探更激进）。
  • 收到协议栈 -ENOMEM（内部缓冲耗尽）就 减半，并保留未发送前缀重试更小的包。

这个策略自动收敛到当前连接能承受的最大速率——强链路提速、弱链路降速，全程无需人工配置。这是我们把这个 “网络层思维” 搬到 MCU 通信上最得意的一笔。

图：BLE 批量发送的自适应调节逻辑。

第五章：可靠性——看门狗与资源监控

1. 看门狗：一个可远程 “自杀” 的保命链

硬件看门狗是最后一道防线，我们把它做成了 独立任务 + 故障注入：

  • 正常模式：VPI 软件定时器每 2500ms hal_wdt_reload() 喂狗（WDT 超时 5000ms，留 2500ms 容错余量）。
  • 故障注入：App 写 0x01 → 点亮蓝灯、停掉喂狗定时器、system_enter_fault() 挂起业务任务 → 约 5s 后 WDT 超时硬件复位。

图：故障注入后的蓝灯指示与复位行为。

这个机制的价值不只是验证 WDT 本身——它给整个系统提供了一个 远程重启的逃生舱。当出现不可恢复的软件异常时，评审/调试现场可以通过 App 一键把设备打回出厂状态，而不是扒壳短路复位。

2. 资源监控：给每个队列和算法装上 “仪表盘”

我们专门加了一个 resource_stats 监控任务（优先级 1，最低），它不参与业务，只做一件事：统计。

  • 每个队列的发送/接收是否失败、是否积压。
  • 每次算法推理的耗时（毫秒级）。
  • 每个任务的栈高水位（uxTaskGetStackHighWaterMark）。

在开发后期这成了救命工具——算法任务栈从 512 调到 1024 就是靠它发现栈高水位告警后改的；队列偶尔积压也是靠它定位到是 BLE 慢还是 IMU 快。

第六章：算法集成（简述）

算法不是本文重点，只讲嵌入式侧的关键决策。我们集成了两个模型，两者都遵守同一条铁律：端侧零动态内存分配，纯因果推理。

1. 手势识别：冻结基础模型，只训微动作

两级 CNN 级联——50 帧基础模型负责粗分类（抬腕/放下/捏合/握拳），70 帧微动作模型负责区分单次/双次动作。关键决策：基础模型冻结（已是 MCU 上的成熟模型），只训练微动作模型，训练完与旧权重按比例混合，兼顾稳定性与新知识。

模型权重以 const 数组固化进 Flash（gesture_weights.c），运行时全部 static 缓冲区，50Hz 逐帧因果处理。识别结果：捏合、捏合 ×2、握拳、握拳 ×2、抬腕、放下共 6 种，测试集窗口级 F1 均 0.94+。

2. 步态识别：随机森林只管 “状态”，事件检测只管 “时刻”

步态识别拆成两个问题分而治之：**”当前在走路还是跑步？”** 由随机森林（每 10 帧分析 96 帧窗口）回答；**”这一步在哪一帧？”** 由模板互相关/能量峰值检测器回答。只有门控状态与单步候选一致、且通过节律校验时才输出事件。

模型参数 20 棵树、1054 个节点，全部以紧凑结构存 Flash。Event F1 0.8882，最差用户 F1 0.7478，others 误报 2.1 次/分钟。

嵌入式侧的体会：模型训练是一回事，部署是另一回事。整个算法移植的核心工作其实是 把训练时的窗口、状态机、阈值翻译成端侧的确定性逻辑——训练脚本的 step_event_model_v8.py / gesture_model.py 与端侧 C 代码逐行对应，这才保证了 “训练准” 和 “跑起来准” 是一致的。

图：手势（短时动作）与步态（周期运动）共享同一份 IMU 数据、逐帧并行推理。

第七章：复盘——踩过的坑与沉淀

1. 决策清单：为什么是这样

决策 备选方案 为什么选它
多任务 + 队列 裸机轮询 故障隔离、并行开发、实时性可控
ISR 只唤醒 ISR 里读 I2C 避免中断重载、采集与推理解耦
穿戴检测去 DC 直接算方差 重力主导，方差分不开
授时门控 先发后补 错时间戳比没有更糟
AIMD 批量 固定批量 链路质量未知，需自适应
模型零 malloc 运行时 malloc MCU 堆小且碎片化，不可控

2. 踩过的坑

  • BLE -ENOMEM 陷阱：协议栈返回 -ENOMEM 不等于包太大，而是 内部缓冲耗尽。一开始我们把它当成 “改小包” 信号，后来意识到要 “暂停一会儿”——AIMD 减半 + 保留前缀重试才是对的。
  • 穿戴检测误判脱落：初版阈值对称、无防抖，静坐几秒就误报 “脱落”。加 3 秒防抖 + 不对称阈值后解决。
  • 算法任务栈溢出：靠资源监控的栈高水位抓出来的，从 512 调到 1024。
  • other_gestures 里混着走路：直接把全部 others 数据当步态负样本会污染模型，必须按任务分别清洗正负样本。

3. 可复用资产

这套代码的价值在于它的 骨架 是可复用的。如果下次要做 “传感器 + 算法 + BLE” 的可穿戴设备，可以原样拿走的：

  • wd_queue / algorithm_queue / result_bus 的 多消费者扇出 + 结果总线 模式。
  • ble_task 的 AIMD 自适应批量 + 断连缓存重发 完整实现。
  • wear_detect 的 去 DC + 迟滞状态机 检测范式。
  • resource_stats 的 资源监控任务。
  • 三个 GATT 服务的 回调注册解耦 模式。
