关于MCU的碎碎念

写于：2026-05-16

第一章：MCU的基础概念理解

首先需要理解，到底什么叫MCU，手机上的芯片算MCU吗？并不是，手机芯片属于SOC，下面介绍他们的基本概念：

MCU 也就是微控制器，片内集成小容量内置 Flash 与 RAM，常见的采用低功耗的 Cortex-M 类内核，主频低、算力有限，无需外接存储即可独立工作，主要用于硬件实时控制，运行裸机或 FreeRTOS 这类轻量化实时系统；

而 SoC 为片上系统，搭载 Cortex-A 等高性能多核架构，运算能力强，基本无大容量片内存储，必须外挂 DDR 内存与固态闪存，可运行 Linux、安卓等完整大型操作系统，集成网络、图像、多媒体等复杂外设，专门应对复杂运算、人机交互、AI、多媒体等高端智能场景。

MCU 的重要组成部分

MCU（微控制器）内部集成了Flash（非易失性程序存储器）和RAM（易失性随机存取存储器）两大核心存储单元，二者分工明确、协同工作，支撑程序从编写、编译、烧录到上电运行的全流程。

Flash属于掉电不丢失的静态存储，是程序的永久载体；我们编写的 C 语言代码，会经过编译器的预处理、编译、汇编、链接四大流程，将代码逻辑转换为 CPU 可执行的二进制机器码，同时按规则划分成不同段：.isr_vector中断向量表、.text代码段（存储所有函数、任务、运算、硬件操作的机器指令）、.rodata只读数据段（存储字符串、const 常量），以及.data段的初始值副本，最终打包成.bin/.hex文件通过烧录工具写入 Flash。

RAM属于掉电丢失的运行时内存，仅在程序上电运行时使用，专门存储程序运行过程中的动态数据，内部按功能划分为四个区域：.data段（存放已初始化的全局 / 静态变量，上电后从 Flash 拷贝初始值）、.bss段（存放未初始化的全局 / 静态变量，上电自动清零）、堆区（Heap）（从低地址向高地址生长，用于动态内存分配、FreeRTOS 任务 / 信号量 / 队列的内存申请）、栈区（Stack）（从高地址向低地址生长，用于存储函数局部变量、函数调用现场、RTOS 任务独立栈）。

MCU 上电后，会从 Flash 起始地址启动（若有 Bootloader 则优先执行引导程序），完成 RAM 的数据搬运与初始化后，跳转至 main 函数执行业务代码，CPU 持续从 Flash 的.text段读取指令，在 RAM 中操作变量数据，最终实现完整的程序运行。

↳ 子段（编译器细分） .isr_vector 中断入口（APP 区最前面）

3. MCU 上电后启动流程

  • 🔌 上电复位
  • 🛠️ 硬件取指：Flash 0x08000000 (Bootloader 起始地址)
  • 🤖 运行 Bootloader：时钟初始化 → 校验 APP 合法性 → 无升级则跳转 APP
  • 🚀 跳转到 APP 分区 (如:0x08010000)
  • 📦 执行 APP 复位汇编：初始化栈 → 搬运 .data → 清零 .bss
  • ▶️ 进入 main() 函数：硬件初始化 → 创建 RTOS 任务/信号量
  • ⚙️ 启动 RTOS 调度器 → 多任务(ADC/保存)并发运行

4. C 语言编译流程

  1. 预处理：展开头文件、宏定义，去掉注释（例：#include "stdio.h"）
  2. 编译（C → 汇编）：把 C 代码翻译成汇编助记符
  3. 汇编（汇编 → 机器码）：把汇编翻译成二进制机器码，生成 .o 目标文件
  4. 链接（链接 .o 文件）：合并所有 .o 文件，分配 Flash/RAM 地址，生成可烧录的 .bin/.hex 文件

第二章：如何分析map文件

单片机开发中的 .map 文件（映射文件）是编译器和链接器（Linker）在编译完成后生成的一份“内存账本”。它详细记录了程序中所有的代码（函数）、变量、常量以及第三方库是如何被分配到单片机的物理内存（Flash 和 RAM）中的。

当需要进行底层调试、优化内存占用，或者实现 A&B 冗余程序设计等复杂的固件架构时，阅读和分析 .map 文件是一项必不可少的硬核技能。可以从下到上、由宏观到微观来拆解它的结构和分析方法：

第一步：看宏观总结（Image component sizes）

分析 .map 文件，最先要看的是文件最末尾的总结部分。这决定了你的程序是否超出了芯片的容量。

在你的文件中，末尾显示：

Total RO  Size (Code + RO Data)                28836 (  28.16kB)
Total RW  Size (RW Data + ZI Data)             22160 (  21.64kB)
Total ROM Size (Code + RO Data + RW Data)      29012 (  28.33kB)

这几个英文缩写代表了内存消耗的核心指标：

  • Code (代码): 存放程序的机器指令（如你写的 C 语言逻辑、卡尔曼滤波算法等）。
  • RO Data (Read-Only Data): 只读常量（如 const 修饰的数组、字符串、程序中定义的绝对地址）。
  • RW Data (Read-Write Data): 已初始化且初值非 0 的全局变量和静态变量。
  • ZI Data (Zero-Initialized Data): 未初始化或初值为 0 的全局变量和静态变量。

如何计算实际占用？

  • Flash 占用 (Total ROM Size) = Code + RO Data + RW Data。因为 RW Data 的初始值需要掉电保存，所以必须存一份在 Flash 里。你的程序目前占用了 28.33kB 的 Flash。
  • RAM 占用 (Total RW Size) = RW Data + ZI Data。单片机上电时，会将 RW Data 从 Flash 搬运到 RAM，并在 RAM 中为 ZI Data 分配清零的空间。你的程序目前占用了 21.64kB 的 RAM。

第二步：查内存大户（Object Totals）

如果发现 RAM 或 Flash 占用过高，向上滚动到 Image component sizes 的明细表格。这里列出了每个 .o 文件（即每个 .c 源文件编译后的产物）的具体开销。

以你的文件为例：

  • FreeRTOS 的堆内存消耗极大： heap_4.o 占用了 10240 Bytes (10kB) 的 ZI Data。这正是 FreeRTOS 配置文件中定义的 configTOTAL_HEAP_SIZE。
  • 主函数与全局缓冲： main.o 占用了 5936 Bytes 的 ZI Data。
  • FatFS 文件系统与显示： ff.o (FatFS核心) 占用了近 5kB 代码；oled.o 占用了 2kB 的 RO Data（通常是字库）。

通过这里，你可以精准定位是哪个模块吃掉了内存。如果在处理 ADC 采集信号并进行复杂滤波时发现 RAM 不够，就可以在这里查看各个缓冲数组到底占了多少空间。

第三步：看物理映射（Memory Map of the image）

这一节展示了代码和数据在单片机真实物理地址上的分布。

  • Load Region LR_1 (Base: 0x08000000…)： 这是程序在 Flash 中的加载区域，0x08000000 是 STM32 标准的 Flash 起始地址。如果是做 OTA 升级，Bootloader 和 App 的偏移地址就是通过核对这里的 Base 地址来确认是否修改成功的。
  • Execution Region ER_RW / ER_ZI (Base: 0x20000000…)： 这是程序运行时的 SRAM 区域，0x20000000 是 STM32 的 RAM 起始地址。

第四步：微观定位（Image Symbol Table）

当你遇到 HardFault（硬件死机）时，这个表格是救命稻草。它记录了每一个函数和全局变量的具体内存地址。

  • 找变量： 比如你在 main.c 中定义了心电图或文件系统相关的缓冲。在这个表中可以搜索到：
    • save_buffer 位于 0x200005d0，大小 2048 字节。
    • wave_buffer2 位于 0x200003c8，大小 520 字节。
  • 找函数定位死机： 如果单片机遇死机，通过调试器查看到 Program Counter (PC 指针) 停在 0x08001bd8。你可以拿着这个地址来查表，由于 ShowECG_task 的地址是 0x08001bd1 且大小为 58 字节，这就说明程序是在执行 ShowECG_task 任务时崩溃的，从而迅速缩小排查范围。

第五步：消除死代码（Removing Unused input sections）

这部分列出了被编译器优化掉的无用函数和变量。比如文件中显示移除了大量 stm32f10x_tim.o 和 stm32f10x_usart.o 中的未调用库函数，总共节省了 33904 bytes。这说明编译器的优化等级（如 Keil 的 Optimization 选项或 --gc-sections 机制）正在正常工作。
